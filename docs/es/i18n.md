# Localización (i18n)

> English: [docs/en/i18n.md](../en/i18n.md)

Idiomas de lanzamiento: **inglés (`en`, idioma fuente y de respaldo) y español (`es`)**.
Agregar un idioma es agregar archivos. No requiere cambios de código.

## 1. Qué se localiza y qué no

| Superficie | ¿Se localiza? | Notas |
|---|---|---|
| Ayuda del CLI, preguntas, progreso, mensajes de éxito/error | ✅ | `any-mcp-codemode --help`, `any-mcp-codemode install`, `any-mcp-codemode import` |
| Errores para el usuario | ✅ mensaje / ❌ código | Cada error tiene un código estable (`CM0102`) y un mensaje localizado. El usuario busca por el código |
| Config generada por `any-mcp-codemode init` | ✅ comentarios | Las claves siguen en inglés; los comentarios generados salen en el idioma del usuario |
| JSON Schema de la config (autocompletado y hover en el editor) | ✅ | `config.schema.json` (en) + `config.schema.es.json`; el `$schema` elige cuál |
| Documentación (`docs/<lang>/`) | ✅ | Mismo árbol de archivos para cada idioma |
| Metadatos de plugins y paquetes (npm, `userConfig` de Claude Code, Hermes, MCPB) | ✅ si el formato lo permite | Si no, en inglés con enlace a `docs/es/` |
| **Claves** de config, **flags** del CLI, nombres de variables de entorno | ❌ | API estable: `limits.timeout_ms`, `--lang`, `AMC_LANG` |
| Protocolo MCP, nombres de herramientas (`code`, `search`, `describe`), campos JSON | ❌ | Contrato con máquinas |
| Logs estructurados (`--log-format json`) | ❌ | `message` en inglés + `code`; los logs son para máquinas y soporte |
| Texto que ve el **modelo** (descripción de la herramienta, tipos TS generados) | ⚙️ ajuste aparte | `model_locale`, por defecto `en`: los modelos rinden mejor y gastan menos tokens en inglés. Las descripciones de las herramientas de origen nunca se traducen |

## 2. Resolución del idioma

Gana la primera coincidencia:

1. Flag `--lang es`
2. Variable `AMC_LANG`
3. `locale` en el archivo de config
4. `LC_ALL` → `LC_MESSAGES` → `LANG` (POSIX, p. ej. `es_CL.UTF-8`)
5. Locale del sistema operativo ([`sys-locale`](https://github.com/1Password/sys-locale): Windows, macOS, Linux, Android, iOS, WASM)
6. `en`

La negociación sigue BCP 47 con una cadena de respaldo: `es-CL → es-419 → es → en`.
Si falta una clave en `es`, en ejecución se usa la de `en`, y la CI falla (ver §5).

`--lang` y `AMC_LANG` solo cambian lo que ve el **usuario**. `model_locale`
controla lo que ve el **modelo**.

## 3. Motor: Project Fluent

[Project Fluent](https://projectfluent.org/) vía [`fluent-rs`](https://github.com/projectfluent/fluent-rs)
(Apache-2.0/MIT, de Mozilla).

- Maneja plurales y selectores reales de CLDR (`{ $count -> [one] … *[other] … }`). El español y otros idiomas los necesitan, y `format!` no los resuelve.
- Las variables tienen nombre, así que los traductores pueden reordenar la frase libremente.
- Weblate y Pontoon editan `.ftl` directamente, así la comunidad puede traducir sin tocar Rust.
- Los `.ftl` se compilan dentro del binario con `include_str!`. Sigue siendo un solo binario y no lee archivos en ejecución. Opcionalmente, `AMC_LOCALES_DIR` permite probar traducciones sin recompilar.

Alternativas descartadas:

- [`rust-i18n`](https://github.com/longbridge/rust-i18n) (YAML, más simple): soporte de plurales débil.
- gettext: cadena de herramientas en C pesada en Windows.

Estructura:

```text
data/locales/
  en/  cli.ftl  errors.ftl  config.ftl  install.ftl
  es/  cli.ftl  errors.ftl  config.ftl  install.ftl
```

El ejemplo de `.ftl` con plurales está en [docs/en/i18n.md](../en/i18n.md#3-engine-project-fluent).

En el código no hay textos literales para el usuario. Todo pasa por
`t!("CM0102", server = …, seconds = …)`, y un lint (§5) lo obliga.

## 4. Configuración

```jsonc
{
  "$schema": "https://<docs-host>/schema/config.schema.es.json",
  "locale": "es",          // opcional; si no, se detecta
  "model_locale": "en",    // idioma de la descripción y los tipos que recibe el modelo
  "servers": { /* … */ }
}
```

- El JSON Schema se genera desde los tipos de Rust (`schemars`). Las descripciones salen de `data/locales/<lang>/config.ftl` (claves `config-<ruta>`), así que código, docs y hover del editor comparten una sola fuente.
- `any-mcp-codemode config explain limits.timeout_ms` muestra la descripción, el valor por defecto y el enlace a la doc en el idioma del usuario.
- Los errores de validación de la config muestran la ruta JSON (en inglés, estable), una explicación localizada y un enlace a `docs/<lang>/config.md#<ancla>`.

## 5. Controles de calidad (CI)

| Control | Falla cuando |
|---|---|
| `i18n-keys` | Una clave existe en `en` pero no en `es` (o al revés) |
| `i18n-vars` | Una traducción usa `{ $variables }` distintas a las de `en` |
| `i18n-unused` | Una clave de los `.ftl` no se usa en el código |
| `no-literal-strings` | Hay `println!`/`eprintln!`/`Display` de error con un literal para el usuario fuera de `t!` |
| `docs-parity` | Un archivo existe en `docs/en/` sin su par en `docs/es/` |
| Tests de snapshot | `any-mcp-codemode --help` para cada idioma (`insta`), así los cambios de texto pasan por revisión |
| Pseudo-locale `en-XA` | Opcional: `[Ŧħïş ïş ŀőŋğëř]` para detectar textos fijos en el código o cortados |

## 6. Proceso

- Un PR que agrega o cambia una clave en `data/locales/en/` también cambia `data/locales/es/` (el control lo obliga). El commit usa el ámbito `i18n` si el cambio es solo de traducción.
- Docs y traducciones van en el mismo commit que la funcionalidad, enlazadas en `Docs:` (ver [commits.md](commits.md)).
- Idiomas nuevos: copiar `data/locales/en/` a `data/locales/<lang>/`, traducir y agregar `docs/<lang>/`. Weblate puede abrir PRs automáticamente.
